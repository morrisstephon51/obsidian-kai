# Problem-Solving Style

Stefan's default approach to a new problem: (1) frame it within the existing mission/brand if possible, (2) build or invoke a structured framework to think it through (LLM Council, five-document process), (3) build a tool or agent if the problem recurs, (4) research extensively if external knowledge is needed (grant landscapes, dev workflows).

This is a **builder's approach to problem-solving** — the instinct is almost always toward construction (a document, an agent, a system) rather than toward conversation, negotiation, or simply doing the manual version first to validate the need. The content automation pipeline, Architect Agent, and Grant Research Agent all reflect "build the tool for this" as a first-line response.

When troubleshooting technical problems (Supabase migration conflicts, cron job frequency limits), the approach is hands-on and persistent — he stays in the code rather than abandoning the approach or outsourcing it.

For relationship/institutional problems (BigHeart recognition, grant funder relationships), the approach is more strategic/preparatory — researching, framing, drafting — but the actual *human* step (the conversation, the meeting, the ask) is less visible in the conversation history relative to the preparation for it. This may simply reflect what gets discussed with Claude vs. what happens in person — but it's worth Stefan checking whether preparation is substituting for the actual ask.
